# 소개

지금쯤이면 Pintos의 내부 동작에 대해 어느 정도 익숙해졌을 것입니다. 여러분의 운영체제는 적절한 동기화로 여러 실행 스레드를 올바르게 처리할 수 있고, 여러 사용자 프로그램을 동시에 로드할 수 있습니다. 하지만 실행될 수 있는 프로그램의 수와 크기는 기계의 주기억장치(main memory) 크기에 의해 제한됩니다. 이 과제에서는 무한 메모리의 환상을 구현하여 그 제한을 제거합니다.

이 과제는 이전 과제 위에 구축됩니다. 프로젝트 2의 테스트 프로그램은 프로젝트 3에서도 동작해야 합니다. 프로젝트 3을 시작하기 전에 프로젝트 2 제출물의 버그를 먼저 수정하세요. 그 버그들이 프로젝트 3에서도 동일한 문제를 일으킬 가능성이 높습니다.

프로젝트 3에서는 학습 편의를 위해 단계별 지침을 제공합니다.

## 배경

### 소스 파일

이 과제는 `vm` 디렉터리에서 작업합니다. Makefile은 `-DVM` 설정을 켜도록 업데이트되어 있습니다. 템플릿 코드가 대량으로 제공되며, 반드시 주어진 템플릿을 따라야 합니다. 즉, 제공된 템플릿을 기반으로 하지 않은 코드를 제출하면 0점을 받습니다. 또한 템플릿에서 "DO NOT CHANGE"로 표시된 부분은 절대 변경해서는 안 됩니다. 아래는 여러분이 수정할 주요 템플릿 파일들에 대한 설명입니다.

- `include/vm/vm.h`, `vm/vm.c`

	가상 메모리에 대한 일반 인터페이스를 제공합니다. 헤더 파일에서 `VM_UNINIT`, `VM_ANON`, `VM_FILE`, `VM_PAGE_CACHE` 등 구현해야 할 `vm_type`의 정의와 설명을 확인할 수 있습니다(`VM_PAGE_CACHE`는 프로젝트 4용이므로 지금은 무시하세요). 또한 여기에서 보조 페이지 테이블(supplemental page table)을 구현하게 됩니다。

- `include/vm/uninit.h`, `vm/uninit.c`

	초기화되지 않은 페이지(`vm_type = VM_UNINIT`)에 대한 연산을 제공합니다。 현재 설계에서는 모든 페이지가 처음에는 초기화되지 않은 상태로 생성되고, 이후 익명 페이지나 파일 기반 페이지로 변환됩니다。

- `include/vm/anon.h`, `vm/anon.c`

	익명 페이지(`vm_type = VM_ANON`)에 대한 연산을 제공합니다。

- `include/vm/file.h`, `vm/file.c`

	파일 기반 페이지(`vm_type = VM_FILE`)에 대한 연산을 제공합니다。

- `include/vm/inspect.h`, `vm/inspect.c`

	채점용 메모리 검사 기능을 포함합니다。 이 파일들은 변경하지 마세요。

대부분의 코드 작성은 `vm` 디렉터리와 이전 과제에서 도입된 파일들에서 이루어질 것입니다。 새로 접하게 될 파일은 다음과 같은 것들이 있을 수 있습니다：

- `include/devices/block.h`, `devices/block.c`

	섹터 단위의 블록 장치 읽기/쓰기 접근을 제공합니다。 스왑 파티션에 접근할 때 이 인터페이스를 사용합니다。

### 메모리 용어

메모리와 스토리지 관련 용어를 정의합니다。 일부 용어는 프로젝트 2(가상 메모리 레이아웃)에서 익숙할 수 있지만, 많은 부분이 새롭습니다。

#### 페이지

페이지(가상 페이지)는 길이가 4,096바이트(페이지 크기)인 연속된 가상 메모리 영역입니다。 페이지는 페이지 정렬(page-aligned)되어야 하며, 즉 페이지 크기로 나누어떨어지는 가상 주소에서 시작해야 합니다。 따라서 64비트 가상 주소의 하위 12비트가 페이지 오프셋(offset)이 됩니다。 상위 비트들은 곧 설명할 페이지 테이블의 인덱스를 나타냅니다。 64비트 시스템에서는 4단계 페이지 테이블을 사용하므로 가상 주소는 다음과 같이 분해됩니다：

63          48 47            39 38            30 29            21 20         12 11         0
+-------------+----------------+----------------+----------------+-------------+------------+
| Sign Extend |    Page-Map    | Page-Directory | Page-directory |  Page-Table |    Page    |
|             | Level-4 Offset |    Pointer     |     Offset     |   Offset    |   Offset   |
+-------------+----------------+----------------+----------------+-------------+------------+
							|                |                |                |             |            |
							+------- 9 ------+------- 9 ------+------- 9 ------+----- 9 -----+---- 12 ----+
														Virtual Address

각 프로세스는 `KERN_BASE`(0x8004000000) 이하의 사용자(가상) 페이지 집합을 독립적으로 가집니다。 반면 커널(가상) 페이지 집합은 전역적이며, 어떤 스레드나 프로세스가 실행되더라도 같은 위치에 존재합니다。 커널은 사용자와 커널 페이지 모두 접근할 수 있지만, 사용자 프로세스는 자신의 사용자 페이지만 접근할 수 있습니다。 자세한 내용은 "가상 메모리 레이아웃(Virtual Memory Layout)"을 참조하세요。

Pintos는 가상 주소를 다루기 위한 여러 유용한 함수를 제공합니다。 자세한 내용은 "가상 주소(Virtual Addresses)"를 참조하세요。

#### 프레임(Frames)

프레임(물리 프레임 또는 페이지 프레임)은 물리 메모리의 연속된 영역입니다。 페이지와 마찬가지로 프레임도 페이지 크기이며 페이지 정렬되어야 합니다。 따라서 64비트 물리 주소는 프레임 번호와 오프셋으로 나눌 수 있습니다：

									12 11         0
			+-----------------------+-----------+
			|      Frame Number     |   Offset  |
			+-----------------------+-----------+
							Physical Address

x86-64는 물리 주소로 직접 메모리를 접근하는 방법을 제공하지 않습니다。 Pintos는 커널 가상 메모리를 물리 메모리에 직접 매핑함으로써 이를 우회합니다 — 커널 가상 메모리의 첫 페이지는 물리 메모리의 첫 프레임에, 두 번째 페이지는 두 번째 프레임에 매핑되는 식입니다。 따라서 프레임은 커널 가상 메모리를 통해 접근할 수 있습니다。

Pintos는 물리 주소와 커널 가상 주소 간의 변환을 위한 함수를 제공합니다。 자세한 내용은 "가상 주소(Virtual Addresses)"를 참조하세요。

#### 페이지 테이블

페이지 테이블은 CPU가 가상 주소를 물리 주소(즉 페이지를 프레임으로)로 변환하는 데 사용하는 자료구조입니다。 페이지 테이블의 형식은 x86-64 아키텍처에 의해 정해집니다。 Pintos는 `threads/mmu.c`에 페이지 테이블 관리 코드를 제공합니다。

다음 다이어그램은 페이지와 프레임 간의 관계를 보여줍니다。 왼쪽의 가상 주소는 페이지 번호와 오프셋으로 구성됩니다。 페이지 테이블은 페이지 번호를 프레임 번호로 번역하고, 변환된 프레임 번호에 오프셋을 결합하여 오른쪽의 물리 주소를 얻습니다。

							+----------+
			 .--------------->|Page Table|-----------.
			/                 +----------+            |
			|   12 11 0                               V  12 11 0
		+---------+----+                         +---------+----+
		| Page Nr | Ofs|                         |Frame Nr | Ofs|
		+---------+----+                         +---------+----+
		 Virt Addr   |                            Phys Addr    ^
						\_______________________________________/

#### 스왑 슬롯(Swap Slots)

스왑 슬롯은 스왑 파티션에 있는 페이지 크기 단위의 디스크 영역입니다。 하드웨어 제약으로 슬롯 배치가 프레임보다 더 유연하지만, 페이지 정렬하는 데 불이익이 없으므로 스왑 슬롯도 페이지 정렬하는 것이 좋습니다。

### 자원 관리 개요

다음 자료구조들을 설계/구현해야 합니다：

- 보조 페이지 테이블(supplemental page table)

	페이지 테이블을 보완하여 페이지 폴트 처리를 가능하게 합니다。 아래 "보조 페이지 테이블 관리"를 참조하세요。

- 프레임 테이블(frame table)

	물리 프레임의 추방(eviction) 정책을 효율적으로 구현할 수 있게 합니다。 아래 "프레임 테이블 관리"를 참조하세요。

- 스왑 테이블(swap table)

	스왑 슬롯의 사용 현황을 추적합니다。 아래 "스왑 테이블 관리"를 참조하세요。

세 가지를 완전히 분리된 자료구조로 구현할 필요는 없습니다。 관련 자원을 결합한 통합 자료구조로 처리하는 것이 편리할 수 있습니다。

각 자료구조의 요소が 어떤 정보를 포함해야 할지 결정하고, 자료구조의 범위(프로세스 로컬인지 시스템 전역인지)와 필요한 인스턴스 수를 정하세요。

설계를 단순화하기 위해 이러한 자료구조들을 페이저블하지 않은 메모리(예: `calloc` 또는 `malloc`)에 저장할 수 있습니다。 이렇게 하면 이들 사이의 포인터들이 유효함을 보장할 수 있습니다。

### 구현 선택(성능 관점)

구현 선택지는 배열, 리스트, 비트맵, 해시 테이블 등이 있습니다。 배열은 단순하지만 희소 배열은 메모리를 낭비합니다。 리스트는 간단하지만 긴 리스트를 순회하면 시간이 소요됩니다。 배열과 리스트는 크기 조절이 가능하지만 리스트는 중간 삽입/삭제에 효율적입니다。

Pintos는 `lib/kernel/bitmap.c` 및 `include/lib/kernel/bitmap.h`에 비트맵 자료구조를 제공합니다。 비트맵은 참/거짓 비트 배열로, 동일한 자원 집합의 사용을 추적하는 데 흔히 사용됩니다。Pintos의 비트맵은 고정 크기이며 필요 시 확장할 수 있습니다。

Pintos는 또한 해시 테이블 자료구조를 포함합니다。 해시 테이블은 다양한 크기에서 삽입과 삭제를 효율적으로 지원합니다。

더 복잡한 자료구조는 성능 향상을 줄 수 있지만 구현을 불필요하게 복잡하게 만들 수 있으므로 권장하지 않습니다(예: 균형 이진 트리 등)。

## 보조 페이지 테이블 관리

보조 페이지 테이블은 페이지 테이블 형식의 한계를 보완하기 위해 페이지별 추가 정보를 저장합니다。 흔히 이것도 "페이지 테이블"이라고 부르므로 혼동을 줄이기 위해 "보조(supplemental)"라는 용어를 사용합니다。

보조 페이지 테이블은 최소한 두 가지 용도로 사용됩니다。 가장 중요한 용도는 페이지 폴트 시 커널이 폴트가 발생한 가상 페이지를 조회하여 해당 페이지에 어떤 데이터가 있어야 하는지를 파악하는 것입니다。 두 번째 용도는 프로세스가 종료될 때 어떤 자원을 해제할지 결정하기 위해 보조 페이지 테이블を 참조하는 것입니다。

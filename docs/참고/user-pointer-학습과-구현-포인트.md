# user pointer 학습과 구현 포인트

이 문서는 Pintos syscall 구현에서 `user pointer`를 이해하고, 직접 구현하기 전에 무엇을 알아야 하는지 정리한다.

목표는 바로 정답 코드를 외우는 것이 아니라, 왜 검증이 필요한지 이해하고 스스로 구현 방향을 잡는 것이다.

## 1. 큰 줄기

### user pointer란 무엇인가

`user pointer`는 유저 프로그램이 커널에게 넘기는 주소값이다.

예를 들어 유저 프로그램에서 다음 syscall을 호출한다고 하자.

```c
write(1, buffer, size);
open(file_name);
exec(cmd_line);
read(0, buffer, size);
```

여기서 `buffer`, `file_name`, `cmd_line` 같은 값은 모두 유저 프로그램의 가상 주소다. 커널은 syscall handler에서 이 값을 받아 사용하지만, 그 주소가 안전하다고 가정하면 안 된다.

유저 프로그램은 정상적인 포인터를 넘길 수도 있지만, 다음처럼 잘못된 포인터를 넘길 수도 있다.

- `NULL`
- 매핑되지 않은 주소
- 커널 영역 주소
- 시작 주소만 유효하고 중간에 끊기는 버퍼
- 문자열 끝의 `\0`을 만나기 전에 invalid page로 넘어가는 주소
- 읽어야 하는데 읽을 수 없는 주소
- 써야 하는데 쓸 수 없는 주소

따라서 syscall 구현에서 user pointer 검증은 선택 사항이 아니라 커널 안정성을 위한 필수 작업이다.

### 왜 커널은 user pointer를 믿으면 안 되는가

커널은 모든 프로세스보다 높은 권한으로 실행된다. 커널이 잘못된 주소를 그대로 역참조하면 단순히 유저 프로그램 하나가 죽는 수준이 아니라 커널 전체가 panic 날 수 있다.

예를 들어 `write(1, bad_ptr, 100)`이 들어왔을 때 커널이 바로 `putbuf(bad_ptr, 100)`을 호출하면, `bad_ptr`이 매핑되지 않은 주소일 때 page fault가 발생한다. 이 page fault를 올바르게 처리하지 못하면 테스트가 실패하거나 커널이 종료된다.

또 더 위험한 경우는 유저가 커널 주소를 넘기는 것이다. 커널이 이 주소를 읽거나 쓰게 되면 유저 프로그램이 커널 메모리에 영향을 줄 수 있다. 운영체제는 유저 영역과 커널 영역을 분리해야 하므로, 이런 접근은 반드시 막아야 한다.

### syscall에서 user pointer가 등장하는 위치

모든 syscall 인자가 pointer인 것은 아니다. fd, size, exit status 같은 값은 정수다. 하지만 다음처럼 메모리 주소를 넘기는 syscall은 pointer 검증이 필요하다.

- `write(fd, buffer, size)`: `buffer`에서 `size` 바이트를 읽는다.
- `read(fd, buffer, size)`: `buffer`에 `size` 바이트를 쓴다.
- `open(file)`: `file` 문자열을 읽는다.
- `create(file, initial_size)`: `file` 문자열을 읽는다.
- `remove(file)`: `file` 문자열을 읽는다.
- `exec(cmd_line)`: `cmd_line` 문자열을 읽는다.

즉 syscall을 구현할 때는 먼저 “이 인자가 주소인가?”를 구분해야 한다. 주소라면 “몇 바이트를 어떤 권한으로 접근하는가?”를 생각해야 한다.

### 검증의 핵심 질문

user pointer 검증은 결국 아래 질문에 답하는 일이다.

1. 이 주소가 유저 영역 주소인가?
2. 이 주소가 현재 프로세스의 page table에 매핑되어 있는가?
3. 이 주소 범위 전체가 유효한가?
4. 이 syscall은 이 주소를 읽는가, 쓰는가?
5. 문자열이라면 `\0`을 만날 때까지 안전하게 읽을 수 있는가?

시작 주소 하나만 검사하는 것은 부족하다. 버퍼는 범위이고, 문자열은 끝 위치가 동적으로 결정되기 때문이다.

## 2. 구현 전 알아야 하는 개념

### 유저 주소와 커널 주소

Pintos에는 유저 가상 주소와 커널 가상 주소의 경계가 있다. 유저 프로그램이 커널 영역 주소를 넘기면 커널은 거부해야 한다.

구현할 때는 보통 `is_user_vaddr()` 같은 함수를 이용해 주소가 유저 영역인지 확인한다.

중요한 점은 `is_user_vaddr()`만으로는 충분하지 않다는 것이다. 이 함수는 주소 범위가 유저 영역인지 알려줄 뿐, 실제로 해당 주소가 현재 프로세스의 page table에 매핑되어 있는지는 보장하지 않는다.

따라서 보통 다음 두 가지를 함께 생각해야 한다.

- 주소가 유저 영역인가?
- 그 주소가 실제 물리 페이지에 매핑되어 있는가?

### page table과 매핑 여부

가상 주소는 page table을 통해 물리 메모리에 매핑된다. 유저 주소처럼 생겼더라도 page table에 매핑되어 있지 않으면 접근할 수 없다.

Pintos에서는 현재 프로세스의 page table을 통해 특정 유저 가상 주소가 실제 페이지에 매핑되어 있는지 확인해야 한다.

이때 주소 하나가 아니라 page 단위로 생각하는 것이 중요하다. 예를 들어 `buffer`가 page 끝 근처를 가리키고 `size`가 크면, 첫 page는 유효하지만 다음 page가 invalid일 수 있다.

### 버퍼 검증

버퍼 검증은 `buffer`부터 `buffer + size - 1`까지 접근 가능한지 확인하는 것이다.

예를 들어 `write(fd, buffer, size)`는 커널이 유저 버퍼를 읽는 syscall이다. 따라서 이 범위는 커널 입장에서 읽을 수 있어야 한다.

반대로 `read(fd, buffer, size)`는 커널이 유저 버퍼에 데이터를 써야 한다. 따라서 이 범위는 쓸 수 있어야 한다.

처음 구현할 때는 최소한 다음을 확인해야 한다.

- `buffer`가 `NULL`이 아닌가?
- 시작 주소가 유저 주소인가?
- 끝 주소까지 유저 주소 범위 안인가?
- 범위 안의 각 page가 매핑되어 있는가?

주의할 점은 `buffer + size` 계산에서 overflow가 날 수 있다는 것이다. 구현할 때는 주소 계산을 조심해야 한다.

### 문자열 검증

문자열 검증은 버퍼 검증보다 조금 다르다. `open(file)`에서 `file`은 길이가 따로 전달되지 않는다. `\0`을 만날 때까지 읽어야 한다.

따라서 문자열 포인터 검증은 다음 방식으로 생각할 수 있다.

1. 현재 문자의 주소가 유저 영역인지 확인한다.
2. 현재 문자의 주소가 매핑되어 있는지 확인한다.
3. 문자를 읽는다.
4. 문자가 `\0`이면 검증 성공이다.
5. 아니면 다음 주소로 넘어간다.

문자열은 page 경계를 넘어갈 수 있으므로, 첫 문자 주소만 검사하면 안 된다.

### 읽기 검증과 쓰기 검증

모든 pointer 검증이 같은 것은 아니다.

`write()`의 `buffer`는 커널이 읽기만 한다. 유저 버퍼의 내용을 가져와서 파일이나 콘솔에 출력하기 때문이다.

`read()`의 `buffer`는 커널이 쓴다. 키보드나 파일에서 읽은 데이터를 유저 버퍼에 저장해야 하기 때문이다.

따라서 구현할 때는 pointer마다 접근 방향을 구분해야 한다.

- 커널이 유저 메모리를 읽는 경우: read 검증
- 커널이 유저 메모리에 쓰는 경우: write 검증

Pintos 기본 단계에서는 page가 매핑되어 있는지만 확인하는 방식으로 시작할 수 있지만, VM 단계까지 고려하면 writable 여부도 중요해진다.

## 3. 구현하기 위해 알아야 하는 포인트

### 어디에서 검증할 것인가

검증 위치는 크게 두 가지 방식이 있다.

1. syscall handler에서 syscall별로 검증한다.
2. helper 함수를 만들고 syscall별 구현 함수에서 호출한다.

처음에는 helper 함수를 만드는 편이 좋다. 예를 들어 개념적으로는 다음 역할의 함수들이 있으면 사고가 정리된다.

- 단일 주소가 유효한지 확인하는 함수
- 버퍼 범위가 유효한지 확인하는 함수
- 문자열이 유효한지 확인하는 함수

이렇게 나누면 `write`, `read`, `open`, `exec`에서 중복을 줄일 수 있다.

### 어떤 syscall에 어떤 검증이 필요한가

구현 전에 표로 정리해두면 실수를 줄일 수 있다.

| syscall | pointer 인자 | 접근 방향 | 검증 방식 |
| --- | --- | --- | --- |
| `write(fd, buffer, size)` | `buffer` | 커널이 읽음 | 버퍼 범위 검증 |
| `read(fd, buffer, size)` | `buffer` | 커널이 씀 | 버퍼 범위 검증 |
| `open(file)` | `file` | 커널이 읽음 | 문자열 검증 |
| `create(file, size)` | `file` | 커널이 읽음 | 문자열 검증 |
| `remove(file)` | `file` | 커널이 읽음 | 문자열 검증 |
| `exec(cmd_line)` | `cmd_line` | 커널이 읽음 | 문자열 검증 |

### 실패하면 어떻게 처리할 것인가

잘못된 user pointer가 들어왔을 때는 보통 해당 유저 프로세스를 종료한다. Pintos userprog 테스트에서는 bad pointer를 넘겼을 때 커널이 죽지 않고 해당 프로세스만 종료되는지를 확인한다.

구현 전 정해야 할 정책은 다음과 같다.

- 잘못된 pointer를 발견하면 즉시 `exit(-1)` 처리할 것인가?
- syscall 함수가 error code를 반환하게 할 것인가?
- lock을 잡은 뒤 pointer 오류가 나면 lock 해제를 어떻게 보장할 것인가?

처음에는 pointer 검증을 lock 획득 전에 끝내는 흐름이 안전하다. lock을 잡은 상태에서 invalid pointer 때문에 프로세스를 종료하면 lock이 해제되지 않는 문제가 생길 수 있다.

### size가 0인 버퍼

`size == 0`이면 실제로 접근할 바이트가 없다. 이 경우 `buffer`를 엄격하게 검사해야 하는지 정책을 정해야 한다.

많은 구현에서는 `size == 0`이면 버퍼에 접근하지 않으므로 성공 처리하거나 0을 반환한다. 하지만 테스트와 구현 스타일에 맞춰 일관되게 처리해야 한다.

### page 경계

가장 자주 놓치는 부분이 page 경계다.

예를 들어 page 크기가 4096바이트이고 `buffer`가 page 마지막 2바이트를 가리킨다고 하자. `size`가 10이면 첫 2바이트는 유효해도 다음 8바이트는 다음 page에 있다. 다음 page가 매핑되지 않았다면 invalid pointer다.

따라서 버퍼 검증은 범위 안의 모든 page를 확인해야 한다.

### 문자열의 최대 길이

문자열은 `\0`을 만날 때까지 계속 읽는다. 그런데 유저가 `\0`이 없는 문자열처럼 보이는 메모리를 넘기면 커널이 너무 오래 검사할 수 있다.

처음 구현에서는 page를 넘을 때마다 유효성을 검사하면서 `\0`을 찾는 방식이 핵심이다. 필요하다면 과제 기준이나 기존 코드 스타일에 맞춰 최대 길이 제한을 둘 수도 있다.

### user pointer와 lock 순서

권장 흐름은 보통 다음과 같다.

1. syscall 번호와 인자를 읽는다.
2. user pointer를 검증한다.
3. 필요한 커널 자료구조를 찾는다.
4. 파일 시스템 lock을 잡는다.
5. 파일 시스템 연산을 수행한다.
6. lock을 해제한다.
7. 반환값을 저장한다.

이 순서를 지키면 invalid pointer 때문에 lock 해제가 꼬이는 일을 줄일 수 있다.

## 4. 직접 구현할 때의 점검 질문

구현 중간에 아래 질문에 답해보면 좋다.

1. 이 syscall의 인자 중 pointer가 무엇인가?
2. 그 pointer는 문자열인가, 고정 길이 버퍼인가?
3. 커널이 그 메모리를 읽는가, 쓰는가?
4. 시작 주소만 검사하고 끝내지는 않았는가?
5. page 경계를 넘어가는 경우도 검사하는가?
6. invalid pointer일 때 커널 panic이 아니라 유저 프로세스 종료로 이어지는가?
7. lock을 잡기 전에 pointer 검증을 끝냈는가?
8. `size == 0`일 때 동작이 일관적인가?
9. `NULL`, 커널 주소, unmapped 주소, page boundary 테스트를 생각해봤는가?

## 5. 관련 테스트를 읽는 방법

Pintos 테스트는 user pointer의 의도를 잘 보여준다. 테스트 파일을 읽을 때는 "어떤 나쁜 포인터를 넘기고 있는가"를 보면 된다.

예를 들어 다음 계열을 보면 좋다.

- `write-bad-ptr.c`: `write()`에 잘못된 buffer를 넘겼을 때 커널이 안전하게 처리하는지 본다.
- `read-bad-ptr.c`: `read()`에 잘못된 output buffer를 넘겼을 때를 본다.
- `open-bad-ptr.c`: 문자열 포인터 검증을 본다.
- `exec-bad-ptr.c`: command line 문자열 검증을 본다.
- `*-boundary.c`: page 경계 근처 포인터 처리를 본다.

테스트를 읽을 때는 expected output보다 먼저 syscall 인자를 보자. 어떤 pointer가 invalid이고, 커널이 어디서 검증해야 하는지 추적하는 연습이 중요하다.

## 6. 구현 방향을 잡기 위한 작은 로드맵

처음부터 모든 syscall을 완벽히 처리하려고 하면 복잡하다. 다음 순서로 생각하면 좋다.

1. 단일 주소 검증 개념을 잡는다.
2. 버퍼 범위 검증으로 확장한다.
3. 문자열 검증으로 확장한다.
4. `write()`에 먼저 적용한다.
5. `read()`에 적용하면서 쓰기 가능한 버퍼 개념을 생각한다.
6. `open`, `create`, `remove`, `exec`에 문자열 검증을 적용한다.
7. bad pointer 테스트와 boundary 테스트를 보며 빠진 케이스를 보완한다.

이 순서로 가면 user pointer 검증이 syscall 전체에 어떻게 퍼지는지 자연스럽게 보인다.

## 7. 한 줄 정리

user pointer 검증은 "유저가 준 주소를 커널이 믿지 않기 위한 장치"다. 구현할 때는 주소 하나가 아니라 접근 범위 전체, 접근 방향, page 경계, 문자열 종료 지점을 함께 생각해야 한다.

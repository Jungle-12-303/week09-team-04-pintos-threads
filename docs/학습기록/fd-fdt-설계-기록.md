# fd와 fdt 설계 기록

이 문서는 Pintos `userprog/syscall.c`에서 파일 관련 syscall을 구현하기 위해 `fd`와 `fdt`를 어떻게 이해하고 설계할지 기록한다.

목표는 단순히 `open`, `read`, `write`, `close`를 통과시키는 코드만 남기는 것이 아니다. 유저 프로그램이 사용하는 정수 `fd`와 커널 내부의 `struct file *` 사이에 왜 변환 계층이 필요한지, 그 계층을 각 프로세스가 어떻게 가져야 하는지 설명할 수 있게 만드는 것이다.

## 1. 문제 정의

유저 프로그램은 파일을 직접 `struct file *`로 다루지 않는다. 유저 프로그램은 `open(file)`을 호출해 정수값인 file descriptor, 즉 `fd`를 받고, 이후 `read(fd, buffer, size)`, `write(fd, buffer, size)`, `close(fd)`처럼 그 정수값을 다시 커널에 넘긴다.

커널은 이 `fd`를 이용해 현재 프로세스의 file descriptor table, 즉 `fdt`에서 실제 파일 객체를 찾아야 한다.

따라서 필요한 핵심 기능은 다음과 같다.

- 각 프로세스마다 독립적인 `fdt`를 가진다.
- `open(file_name)`은 파일명을 받아 실제 파일을 열고, 그 파일 객체를 `fdt`에 등록한 뒤 새 `fd`를 반환한다.
- `read`, `write`, `filesize`, `seek`, `tell`, `close`는 파일명이 아니라 이미 발급된 `fd`를 받아 `fdt`에서 `struct file *`를 찾는다.
- 잘못된 `fd`가 들어오면 커널이 죽지 않고 실패값을 반환하거나 프로세스를 종료하는 정책을 적용한다.
- 프로세스가 종료될 때 열린 파일들을 정리한다.

## 2. 구현 전 기초 이론 정리

### 프롬프트의 한계 보정과 설계 확장

처음 떠올린 설명은 "파일 쓰기를 하면 파일명을 받아서 구현한 fdt에 접근해서 있나 없나 보고 fd 값을 가져와 실제 파일 객체에 가서 작업한다"에 가까웠다.

이 직관은 "유저가 파일을 직접 만지지 않고 중간 테이블을 거친다"는 점에서는 맞다. 하지만 syscall 역할이 섞여 있다.

`write`는 파일명을 받지 않는다. `write(fd, buffer, size)`는 이미 열린 파일을 가리키는 `fd`를 받는다. 파일명을 받는 syscall은 `open(file_name)`이고, 이때 파일명을 이용해 `filesys_open()`을 호출한다. `open`이 성공하면 커널은 `struct file *`를 현재 프로세스의 `fdt`에 저장하고, 유저에게는 그 위치를 나타내는 정수 `fd`만 돌려준다.

따라서 설계 질문은 "파일명으로 fdt를 찾는가"가 아니라 다음처럼 바뀌어야 한다.

- `open`이 만든 `struct file *`를 어디에 저장할 것인가
- 유저에게 돌려줄 `fd` 번호는 어떻게 배정할 것인가
- `write(fd, ...)`에서 `fd`를 어떻게 검증하고 `struct file *`로 변환할 것인가
- `fd == 0`, `fd == 1`처럼 표준 입력과 표준 출력은 일반 파일과 어떻게 다르게 처리할 것인가
- 프로세스 종료나 `close(fd)`에서 파일 객체의 생명주기를 어떻게 끝낼 것인가

이 단계에서 바로 배열이나 리스트 중 하나를 고르는 것에 갇히면 안 된다. 먼저 `fd`가 유저에게 보이는 핸들이고, `fdt`가 커널 내부 자원 테이블이라는 역할 분리를 이해해야 한다.

### 기능이 필요한 이유

`struct file *`는 커널 내부 포인터다. 유저 프로그램에게 이 포인터를 그대로 주면 안 된다.

첫째, 유저 프로그램이 커널 주소를 직접 알게 된다. 둘째, 유저가 임의의 값을 포인터처럼 넘겼을 때 커널이 잘못된 메모리를 참조할 위험이 있다. 셋째, 같은 파일을 여러 프로세스가 열었을 때 각 프로세스가 독립적인 file position을 가져야 하는데, 이를 정수 `fd`와 per-process `fdt`로 관리하는 편이 자연스럽다.

그래서 유저에게는 작은 정수 `fd`만 보여주고, 커널은 현재 프로세스의 `fdt` 안에서 그 정수에 대응하는 실제 `struct file *`를 찾는다.

### 관련 개념

`fd`는 유저 프로그램이 열린 파일을 가리키기 위해 사용하는 정수 핸들이다.

`fdt`는 한 프로세스가 열어 둔 파일 목록이다. 같은 정수 `fd`라도 프로세스가 다르면 다른 파일을 가리킬 수 있다. 따라서 `fdt`는 전역 테이블이 아니라 각 프로세스가 가져야 한다.

`struct file *`는 커널 파일 시스템이 실제 열린 파일을 표현하는 객체다. Pintos의 `struct file` 안에는 inode, 현재 위치 `pos`, write deny 상태가 들어 있다. `file_read()`, `file_write()`, `file_seek()`, `file_tell()`, `file_close()`는 이 객체를 대상으로 동작한다.

표준 입출력과 에러 출력도 `fd` 체계에 포함된다. 이 설계에서는 `fd == 0`은 stdin, `fd == 1`은 stdout, `fd == 2`는 error 또는 stderr 용도로 예약한다. 일반 파일은 `fd == 3`부터 배정한다.

`fd == 0`, `fd == 1`, `fd == 2`는 일반 파일처럼 `struct file *`를 찾는 대상이 아니라, 필요할 때 `input_getc()` 또는 `putbuf()` 같은 장치 함수와 연결해서 별도로 처리할 수 있다.

### 곁가지 학습: 주소를 표현하는 타입

fd/fdt를 구현하다 보면 syscall 인자로 넘어온 값, 유저 버퍼 주소, 문자열 주소, 커널 객체 포인터를 다루게 된다. 이때 주소처럼 보이는 값을 여러 타입으로 표현할 수 있어서 헷갈릴 수 있다.

`uint64_t`는 64비트 부호 없는 정수다. x86-64 Pintos에서 syscall 인자는 레지스터를 통해 들어오므로 처음에는 `uint64_t`처럼 정수값으로 받기 쉽다. 하지만 이 타입 자체는 "주소"라는 의미를 갖지 않는다. 단지 64비트 숫자일 뿐이다. 따라서 syscall 인자를 임시로 담는 용도에는 자연스럽지만, 포인터처럼 역참조하거나 문자열처럼 순회하려면 의미에 맞는 포인터 타입으로 해석해야 한다.

`uintptr_t`는 포인터 값을 정수로 안전하게 담기 위한 정수 타입이다. 주소를 숫자로 바꿔서 비교하거나, 페이지 경계 계산처럼 산술 처리를 해야 할 때 `uint64_t`보다 의도가 분명하다. 핵심은 "이 값은 일반 숫자가 아니라 포인터에서 온 주소값이다"라는 의미를 드러내는 데 있다.

`void *`는 "아직 어떤 타입을 가리키는지 정하지 않은 포인터"다. 주소 하나의 유효성을 검사하거나, 여러 종류의 포인터를 공통으로 받는 helper에서 쓰기 좋다. 다만 `void *`는 가리키는 원소 크기가 정해져 있지 않기 때문에, 바이트 단위로 이동하거나 문자열처럼 읽으려면 다른 포인터 타입으로 해석해야 한다.

`char *`는 바이트 단위로 이동할 수 있는 포인터다. C 문자열은 `char *`로 다루고, `\0`을 만날 때까지 한 바이트씩 검사한다. 또한 버퍼 주소를 바이트 단위로 순회해야 할 때도 `char *` 또는 비슷한 바이트 포인터 관점이 필요하다.

정리하면 다음과 같다.

- syscall 인자를 처음 받는 레지스터 값: `uint64_t`처럼 정수로 들어올 수 있다.
- 주소값을 숫자로 계산하거나 비교해야 하는 경우: `uintptr_t`가 의미가 더 분명하다.
- 주소 하나를 타입과 무관하게 검사하는 경우: `void *`가 자연스럽다.
- 문자열이나 버퍼를 바이트 단위로 순회하는 경우: `char *` 관점이 필요하다.

중요한 것은 "주소를 저장할 수 있느냐"보다 "그 값을 어떤 의미로 사용할 것인가"다. 같은 비트값이라도 정수로 계산할 때, 포인터 유효성을 검사할 때, 문자열을 읽을 때 선택해야 하는 타입이 달라진다.

### 가능한 설계 대안

대안 A: 고정 크기 배열을 `fdt`로 사용한다.

- 장점: `fd`를 배열 인덱스로 바로 사용할 수 있어 구현이 단순하다.
- 장점: Pintos 기본 프로젝트 수준에서는 열 수 있는 파일 수에 상한을 두어도 충분할 가능성이 크다.
- 단점: 최대 fd 개수를 미리 정해야 한다.
- 단점: 빈 슬롯 탐색과 범위 검사를 실수하면 잘못된 fd 접근이 생길 수 있다.

대안 B: 리스트로 열린 파일 엔트리를 관리한다.

- 장점: 열린 파일 수가 고정되어 있지 않다.
- 장점: `fd`, `struct file *`, list element를 묶은 별도 엔트리 구조를 만들기 쉽다.
- 단점: fd를 찾을 때 리스트를 순회해야 한다.
- 단점: 배열보다 구현해야 할 코드가 많고, 메모리 해제 실수 가능성이 있다.

대안 C: 해시 테이블로 `fd`에서 파일 엔트리를 찾는다.

- 장점: fd 검색이 빠르고 확장성이 좋다.
- 단점: `fd`가 보통 작은 정수라서 배열 인덱스로 바로 접근할 수 있는데, 해시를 쓰면 이 장점을 버리고 hash 계산, bucket 탐색, 충돌 비교를 추가하게 된다.
- 단점: 해시 초기화, 삽입, 삭제, 종료 시 정리까지 관리해야 한다.
- 단점: Pintos 기본 syscall 구현에는 성능상 필요보다 구현 복잡도가 더 큰 설계일 수 있다.

처음에는 해시 테이블을 쓰면 검색이 빠르고 남들이 잘 안 쓰는 구조라서 좋아 보였다. 하지만 `fd`는 해시가 잘 맞는 듬성듬성한 큰 key가 아니라, 보통 `0, 1, 2, 3, ...`처럼 작은 정수부터 배정되는 값이다.

해시는 key 범위가 크고 실제로 쓰이는 값이 흩어져 있을 때 장점이 커진다. 반면 `fd`는 그 자체가 배열 인덱스로 쓰기 좋은 값이다. 따라서 `fd -> file` 조회에서는 해시의 평균 O(1)보다 배열의 직접 인덱싱이 더 단순하고 자연스럽다.

이 판단 때문에 초기 구현 방향은 해시보다 배열 쪽으로 기운다. 해시를 쓰는 것이 틀린 것은 아니지만, 이 경우에는 성능상 꼭 필요한 선택이라기보다 해시 자료구조를 연습하기 위한 선택에 가깝다. 지금 목표가 fd/fdt의 기본 의미와 syscall 흐름을 안정적으로 구현하는 것이라면 배열이 더 적절하다.

리스트는 배열과 해시 사이의 대안이다. 엔트리 구조를 명시적으로 만들 수 있다는 장점은 있지만, fd 조회 때마다 순회해야 한다. 열린 파일 수가 많지 않다면 충분히 가능하지만, `fd`가 작은 정수라는 특성을 가장 잘 살리는 쪽은 배열이다.

### Pintos에서 확인해야 할 코드 위치

- `pintos/userprog/syscall.c`: `open`, `read`, `write`, `close` 같은 syscall을 구현하는 위치
- `pintos/include/threads/thread.h`: 각 프로세스가 가질 `fdt` 필드를 추가할 후보 위치
- `pintos/filesys/filesys.c`: 파일명으로 파일을 여는 `filesys_open()` 제공
- `pintos/include/filesys/file.h`: `file_read()`, `file_write()`, `file_close()` 등 실제 파일 객체 조작 API 제공
- `pintos/lib/user/syscall.c`: 유저 프로그램이 호출하는 syscall wrapper 확인
- `pintos/include/lib/syscall-nr.h`: 구현해야 할 파일 관련 syscall 번호 확인

### 구현 전 주의할 점

`open`의 반환값은 `struct file *`가 아니라 `fd`여야 한다. 현재 `sys_open()`이 `filesys_open()` 반환값을 그대로 반환하는 구조라면, 이는 반드시 바뀌어야 한다.

`write(fd, buffer, size)`에서 `fd == 1`은 stdout이므로 지금처럼 `putbuf()`로 처리할 수 있다. `fd == 2`는 error 또는 stderr 용도로 예약할지, stdout과 같은 장치 출력으로 처리할지 정책을 정해야 한다. 일반 파일은 `fd >= 3`부터 현재 프로세스의 `fdt`에서 파일 객체를 찾아 `file_write()`를 호출한다.

`read(fd, buffer, size)`에서 `fd == 0`은 stdin이다. 일반 파일은 `fd >= 3`부터 `fdt`를 통해 파일 객체를 찾고 `file_read()`를 호출한다. 반대로 stdin에 write하거나 stdout/error에서 read하는 경우는 실패 처리 기준을 정해야 한다.

`fd`는 프로세스마다 독립적이어야 한다. 부모와 자식, 또는 서로 다른 프로세스가 같은 숫자 `3`을 갖더라도 같은 파일 객체를 뜻한다고 가정하면 안 된다.

`close(fd)`는 `fdt`에서 엔트리를 제거하고 `file_close()`를 호출해야 한다. 프로세스 종료 시에도 아직 닫히지 않은 파일들을 모두 닫아야 한다.

여기서 중요한 점은 fdt 배열 자체와 fdt가 가리키는 열린 파일 객체의 생명주기가 다르다는 것이다. `struct thread`가 사라지면 그 안의 배열 공간은 같이 사라질 수 있지만, 배열 칸에 들어 있던 열린 파일 객체가 자동으로 닫히는 것은 아니다. 따라서 프로세스 종료 흐름에서 fdt를 순회하며 열어 둔 파일들을 명시적으로 닫는 정리 함수가 필요하다.

파일 시스템 전체가 동시에 접근될 수 있으므로, 프로젝트 요구사항에 따라 전역 파일 시스템 lock이 필요할 수 있다. 이 문제는 `fdt` 자체의 설계와 별개로, 실제 `filesys_*` 또는 `file_*` 호출을 감쌀 때 다시 판단해야 한다.

### 아직 열어둘 설계 선택지

처음 구현은 배열 기반으로 시작하는 쪽이 가장 자연스럽다.

이때 아직 결정해야 할 것은 배열을 어떻게 선언할지가 아니라, 다음 기준들이다.

- 최대 fd 개수를 어느 정도로 제한할 것인가
- `fd == 0`, `fd == 1`, `fd == 2`를 배열에 포함해서 관리할 것인가, 아니면 syscall에서 별도로 처리할 것인가
- `open`에서 빈 fd 번호를 어떻게 찾을 것인가
- `close`로 비워진 fd 번호를 재사용할 것인가
- fd 검증과 파일 객체 조회를 어떤 helper 책임으로 나눌 것인가

## 3. 내가 세운 초기 기준

초기 기준은 다음과 같다.

- `fdt`는 각 프로세스가 가진다.
- `fd`는 유저 프로그램에게 반환되는 정수 핸들이다.
- `open(file_name)`만 파일명을 사용한다.
- `read`, `write`, `filesize`, `seek`, `tell`, `close`는 파일명이 아니라 `fd`를 사용한다.
- `fd`를 실제 파일 객체로 바꾸는 코드는 syscall마다 흩어뜨리지 않고 helper로 분리한다.
- `fd == 0`은 stdin, `fd == 1`은 stdout, `fd == 2`는 error 또는 stderr 용도로 예약하고 일반 파일 fd는 `3`부터 배정한다.
- `fdt` 자료구조는 해시보다 배열을 우선 고려한다. 이유는 `fd`가 보통 작은 연속 정수라서 배열 인덱스로 바로 접근하는 편이 더 단순하고 자연스럽기 때문이다.

## 4. 버전별 설계 변화

### v1. thread에 단순 배열 fdt를 직접 두는 설계

#### 목표

각 프로세스가 자기 fdt를 갖게 만들고, `open`으로 얻은 파일 객체를 fd 번호와 연결할 공간을 먼저 확보하려고 했다.

#### 코드 또는 구조

현재 설계의 핵심은 `struct thread` 안에 `uint64_t fdt[MAX_FD]` 형태의 배열을 직접 두는 것이다.

또한 fdt 조작을 syscall 안에 흩뿌리지 않기 위해 다음 책임을 가진 helper 이름을 잡아두었다.

- `fdt_init`: fdt 초기화
- `fd_alloc`: 빈 fd를 찾아 파일 객체와 연결
- `fdt_find_fd`: fd로 파일 객체 조회
- `fdt_close_fd`: fd 닫기
- `fdt_destroy`: 프로세스 종료 시 fdt 정리

#### 초기 접근의 장점

가장 큰 장점은 단순함이다. fd가 작은 정수이므로 배열 인덱스로 바로 접근할 수 있다. `fd == 3`이면 fdt의 3번 위치를 보면 된다는 식으로 사고할 수 있어서, fd와 fdt의 기본 관계를 이해하기 쉽다.

또한 fdt를 각 `struct thread` 안에 두려는 방향은 맞다. fd는 프로세스마다 독립적인 값이므로, 전역 자료구조가 아니라 현재 실행 중인 프로세스의 상태에 속해야 한다.

helper 이름을 먼저 나눈 것도 좋은 출발점이다. `open`, `read`, `write`, `close` syscall이 직접 배열을 만지기 시작하면 fd 범위 검사와 NULL 검사 기준이 흩어질 수 있다. helper를 두면 fdt 조작 기준을 한곳에 모을 수 있다.

#### 남은 문제

첫 번째 문제는 fdt 원소 타입이다.

현재 `uint64_t` 배열은 파일 객체 포인터를 숫자로 저장하려는 방향에 가깝다. syscall 인자를 레지스터에서 받을 때는 `uint64_t`가 자연스럽지만, fdt가 실제로 저장해야 하는 것은 "열린 파일 객체"다. 따라서 fdt 원소가 숫자여야 하는지, 파일 객체 포인터여야 하는지 다시 판단해야 한다.

두 번째 문제는 빈 fd 탐색 방식이다.

단순 배열에서 `open` 때마다 `3`부터 빈 칸을 찾으면 최악의 경우 O(n) 탐색이 된다. 다만 Pintos에서 동시에 열 파일 수가 아주 크지 않다면, 이 O(n)이 실제 문제가 될 가능성은 낮다. 오히려 단순한 선형 탐색이 구현 실수를 줄일 수 있다.

세 번째 문제는 fdt를 `struct thread`에 직접 배열로 넣을지, 별도의 `struct fdt`로 감쌀지다.

직접 배열은 단순하지만, 나중에 unused fd 관리, 최대 fd, next fd 같은 상태가 늘어나면 `struct thread` 안의 책임이 지저분해질 수 있다.

#### 가능한 대안

대안 A: v1을 유지하고, 빈 fd는 `3`부터 선형 탐색한다.

- 장점: 가장 단순하다.
- 장점: fd 조회는 배열 인덱스로 바로 접근하므로 빠르다.
- 단점: fd 할당 시 빈 칸을 찾는 비용은 O(n)이다.
- 단점: 열린 파일 수가 많고 open/close가 매우 자주 반복되면 비효율이 생길 수 있다.

대안 B: `struct fdt`를 따로 만들고, 그 안에 파일 배열과 사용하지 않는 fd 목록을 함께 둔다.

- 장점: fdt 관련 상태를 `struct thread`에서 분리할 수 있다.
- 장점: 사용하지 않는 fd를 별도로 관리하면 fd 할당 때 빈 칸 탐색을 줄일 수 있다.
- 단점: unused fd 목록을 정렬 상태로 유지하려면 close 때 삽입 위치를 찾아야 한다.
- 단점: 배열 하나만 쓸 때보다 초기화, 삽입, 삭제, 종료 정리가 복잡해진다.

대안 C: v1을 유지하되, 단순 선형 탐색을 보완하는 힌트 값을 둔다.

- 장점: 배열 구조를 유지하면서 매번 처음부터 찾는 비용을 줄일 수 있다.
- 장점: 별도 unused fd 리스트보다 구조가 단순하다.
- 단점: close로 생긴 작은 fd를 얼마나 빨리 재사용할지 정책을 정해야 한다.
- 단점: 힌트 값이 항상 최적 fd를 가리키는 것은 아니므로 결국 탐색이 필요할 수 있다.

#### 채택한 방향

unused fd 리스트를 두는 설계는 아직 다음 버전으로 확정하지 않는다.

현재 고민의 핵심은 "fd 할당의 O(n)을 줄이기 위해 unused fd 리스트를 둘 가치가 있는가"이다. 이론적으로는 unused fd 목록이 있으면 빈 fd를 찾는 비용을 줄일 수 있다. 하지만 정렬된 unused fd 리스트를 유지하려면 close 시점에 정렬 삽입 비용이 생기고, 자료구조를 관리하는 코드도 늘어난다.

따라서 성능만 보면 v2가 항상 더 낫다고 말하기 어렵다. fd 할당이 O(n)인 대신 v1은 단순하고, fd 조회는 여전히 O(1)에 가깝다. Pintos 수준에서 `MAX_FD`가 크지 않다면 선형 탐색 비용보다 구현 복잡도 증가가 더 큰 문제가 될 수 있다.

현재 판단은 v1을 유지하면서 먼저 단순 배열 방식으로 fd/fdt의 기본 흐름을 완성하고, 실제로 빈 fd 탐색이 복잡해지거나 코드가 지저분해질 때 `struct fdt` 분리를 다시 검토하는 것이다.

### v2. void *로 자원을 담을 때 타입 판별이 필요하다는 설계

#### 목표

fdt가 파일뿐 아니라 나중에 socket, directory, 표준 입출력 같은 여러 자원을 담을 수 있다면, 원소 타입을 특정 파일 포인터로 고정하지 않고 더 일반적인 포인터로 둘 수 있는지 검토했다.

#### 코드 또는 구조

현재 고민은 fdt의 각 칸을 "어떤 자원이든 가리킬 수 있는 포인터"처럼 다루는 것이다.

이 방식에서는 fdt 칸이 특정 파일만 가리킨다는 보장이 약해진다. 파일일 수도 있고, 나중에 다른 자원일 수도 있다. 따라서 fdt 칸에서 값을 꺼낸 뒤 무조건 파일 객체처럼 다루면 안 된다.

#### 이전 버전에서 개선된 점

v1에서는 fdt가 사실상 파일 객체만 담는 테이블에 가까웠다. 그런데 fd는 원래 "열린 파일"뿐 아니라 넓게 보면 프로세스가 가진 열린 자원 핸들로 확장될 수 있다.

따라서 자원을 일반 포인터로 저장하려는 생각은 fdt를 더 확장 가능한 구조로 바라보게 만든다.

#### 남은 문제

가장 큰 문제는 타입 정보가 사라진다는 점이다.

일반 포인터 하나만 fdt에 넣으면, 나중에 꺼냈을 때 이것이 파일인지, 디렉터리인지, socket인지, 표준 입출력 같은 특수 fd인지 알 수 없다. 포인터 값 자체에는 "내가 어떤 구조체를 가리킨다"는 런타임 정보가 들어 있지 않다.

따라서 `void *` 같은 일반 포인터를 쓰려면 반드시 별도의 타입 정보가 필요하다. 즉 fdt는 단순히 "자원 포인터 배열"이 아니라 "자원 종류와 자원 포인터를 함께 저장하는 테이블"이 되어야 한다.

이 설계를 하지 않으면 잘못된 캐스팅이 생길 수 있다. 예를 들어 실제로는 directory를 가리키는 값을 file처럼 해석하면, 맞지 않는 함수로 자원을 조작하게 된다. 이런 오류는 컴파일러가 막아주기 어렵다.

#### 가능한 대안

대안 A: fdt를 파일 전용 테이블로 제한한다.

- 장점: 타입이 단순하고 명확하다.
- 장점: 지금 구현하려는 `open`, `read`, `write`, `close`의 기본 흐름에 집중하기 좋다.
- 단점: 나중에 directory나 socket 같은 다른 자원을 같은 fd 체계에 넣으려면 구조를 바꿔야 한다.

대안 B: fdt 원소를 일반 자원 포인터로 두고, 자원 종류를 함께 저장한다.

- 장점: 여러 종류의 자원을 같은 fd table에서 관리할 수 있다.
- 장점: `close` 같은 공통 작업에서 자원 종류에 따라 다른 정리 함수를 선택할 수 있다.
- 단점: fdt 원소가 단순 포인터 하나보다 복잡해진다.
- 단점: 모든 fd 사용 지점에서 자원 종류를 확인해야 한다.

대안 C: 표준 입출력과 파일만 먼저 분리 처리하고, 일반 자원 테이블화는 나중으로 미룬다.

- 장점: 지금 단계에서 구현 범위가 과하게 넓어지지 않는다.
- 장점: `fd == 0`, `fd == 1`, `fd == 2`는 특수 처리하고, `fd >= 3`은 파일로 보는 단순한 기준을 유지할 수 있다.
- 단점: 나중에 다른 자원을 추가할 때 다시 설계를 확장해야 한다.

#### 채택한 방향

현재로서는 대안 C를 우선한다.

Pintos의 현재 목표가 기본 파일 syscall 구현이라면, fdt를 처음부터 모든 자원 타입을 담는 일반 테이블로 만들 필요는 아직 약하다. 먼저 `fd >= 3`은 열린 파일을 가리킨다는 단순한 기준으로 구현하고, 표준 입출력은 fd 번호로 특수 처리한다.

다만 이 과정에서 배운 중요한 점은 남긴다. 일반 포인터를 쓰면 자원을 담을 수 있는 폭은 넓어지지만, 그 포인터가 무엇을 가리키는지 판단할 타입 정보가 사라진다. 따라서 여러 종류의 자원을 fdt에 담고 싶다면 "포인터 + 자원 종류"를 함께 저장하는 구조가 필요하다.

#### 작은 수정 메모

- `void *`를 배열 원소로 쓰면 여러 포인터를 담을 수 있지만, 배열을 지역 변수로 받을 때는 "배열의 원소가 어떤 타입인가"까지 맞춰야 한다.
- fdt 원소가 일반 포인터라면 `NULL`로 빈 칸을 표현하는 것은 자연스럽지만, 꺼낸 뒤 어떤 타입으로 캐스팅할지는 별도 기준 없이는 알 수 없다.
- `thread_current()->fdt`가 `void *` 배열이라면 지역 별명은 `void *` 하나가 아니라 `void **` 관점이어야 한다. 또한 배열 전체 주소인 `&thread_current()->fdt`가 아니라 배열 이름인 `thread_current()->fdt`를 사용해야 `fdt[cur_fd]`처럼 인덱싱할 수 있다.
- 일반 규칙으로 보면, 배열 원소 타입이 `T`이면 그 배열을 인덱싱하며 접근하는 지역 별명은 `T *` 관점이 된다. 예를 들어 `int` 배열은 한 칸이 `int`이므로 배열 접근 별명은 `int *`이고, `void *` 배열은 한 칸이 `void *`이므로 배열 접근 별명은 `void **`가 된다. 즉 `void **`는 갑자기 어려운 이중 포인터가 나온 것이 아니라, "포인터를 원소로 가진 배열"에 접근하기 위한 자연스러운 타입이다.

### 이후 후보. struct fdt와 unused fd 목록 분리

#### 목표

fdt를 단순 배열 멤버가 아니라 별도 구조체로 분리하고, 사용하지 않는 fd를 목록으로 관리해서 fd 할당 책임을 더 명확하게 만들 수 있는지 검토한다.

#### 코드 또는 구조

아이디어는 다음과 같다.

- `struct thread`는 fdt 배열을 직접 갖지 않고 fdt 객체를 멤버로 가진다.
- fdt 객체 안에는 fd에서 파일 객체로 가는 배열이 있다.
- fdt 객체 안에는 현재 사용하지 않는 fd 목록이 있다.
- `open`은 unused fd 목록에서 fd를 하나 꺼내 파일 객체와 연결한다.
- `close`는 fd를 비우고 unused fd 목록에 다시 넣는다.

#### 이전 버전에서 개선될 수 있는 점

fdt 관련 상태를 하나의 구조체로 묶으면 `struct thread`가 덜 지저분해질 수 있다.

또한 사용하지 않는 fd를 따로 관리하면 `open` 때마다 배열 전체를 훑지 않아도 될 가능성이 있다. 특히 가장 작은 사용 가능 fd를 항상 반환하고 싶다면 unused fd 목록을 정렬해두는 방식이 떠오를 수 있다.

#### 남은 문제

정렬된 unused fd 리스트가 실제로 성능을 개선하는지는 애매하다.

fd 할당에서는 빠를 수 있지만, `close` 때 fd를 다시 넣을 위치를 찾아야 한다. 정렬을 유지하려면 이 삽입도 O(n)이 될 수 있다. 결국 비용이 `open`에서 `close`로 옮겨가는 것일 수 있다.

또한 Pintos에서 fd 개수가 작다면 O(n) 선형 탐색 자체가 큰 병목이 아닐 수 있다. 이 경우 unused fd 리스트는 성능 개선보다 구현 복잡도만 늘릴 가능성이 있다.

#### 가능한 대안

대안 A: v1 배열 설계를 유지하고 단순 선형 탐색을 사용한다.

- fd 개수가 작다면 충분히 합리적이다.
- 구현이 단순해서 먼저 syscall 흐름을 완성하기 좋다.

대안 B: 별도 `struct fdt`로만 분리하고, unused fd 리스트는 아직 두지 않는다.

- 책임 분리는 얻고, 자료구조 복잡도는 크게 늘리지 않는다.
- 이후 필요해지면 unused fd 관리 상태를 추가할 수 있다.

대안 C: unused fd 리스트를 두되 정렬을 포기한다.

- 빈 fd를 빠르게 얻는 데 집중할 수 있다.
- 다만 항상 가장 작은 fd를 반환한다는 기준과는 맞지 않을 수 있다.

대안 D: unused fd를 정렬 리스트로 관리한다.

- 가장 작은 fd 재사용 기준을 만족시키기 쉽다.
- 하지만 정렬 삽입과 리스트 관리 비용이 생긴다.

#### 채택한 방향

현재로서는 대안 B가 가장 균형 있어 보인다.

즉, 이후 이 방향을 적용한다면 "성능 최적화"보다 "책임 분리"를 목적으로 `struct fdt`를 먼저 검토한다. unused fd 정렬 리스트는 실제로 fd 할당 정책이 복잡해지거나, 선형 탐색이 문서로 설명하기 어려울 정도로 부담이 될 때 추가로 고려한다.

## 5. 구현 전 임시 설계 기준

아직 최종 설계가 아니다. v1 코드를 기준으로 구현을 진행하면서 계속 검토할 임시 기준이다.

- `struct thread`에 현재 프로세스의 `fdt`를 둔다.
- `fdt`는 해시가 아니라 배열 기반으로 시작하는 것을 우선 검토한다.
- 이후 `struct fdt`로 분리하더라도, 그 목적은 성능 최적화보다 책임 분리에 가깝다.
- unused fd 정렬 리스트는 당장 채택하지 않고, 단순 배열 탐색이 실제로 문제가 되는지 확인한 뒤 검토한다.
- 여러 종류의 자원을 fdt에 담게 된다면, 단순 포인터만 저장하지 말고 자원 종류를 함께 저장하는 구조가 필요하다.
- 일반 파일 fd는 `3`부터 배정한다.
- `open`은 파일명을 받아 `struct file *`를 만들고, `fdt`에 저장한 뒤 fd를 반환한다.
- `read`와 `write`는 fd를 받아 표준 입출력인지 먼저 확인하고, 일반 파일이면 `fdt`에서 파일 객체를 조회한다.
- `close`는 fd 엔트리를 비우고 `file_close()`를 호출한다.
- 프로세스 종료 시 아직 열린 파일을 모두 닫는다.
- fd 검증과 파일 객체 조회는 helper 함수로 분리한다.

## 6. 배운 점

`fd`는 파일명이 아니라 열린 파일 객체를 가리키는 유저용 핸들이다.

`fdt`는 커널 내부의 파일 객체를 유저에게 직접 노출하지 않기 위한 변환 계층이다. 이 테이블이 프로세스마다 있어야 같은 fd 번호라도 각 프로세스에서 독립적인 의미를 가질 수 있다.

`open`은 파일명에서 파일 객체로 넘어가는 syscall이고, `read`와 `write`는 fd에서 파일 객체로 넘어가는 syscall이다. 이 둘을 분리해서 이해해야 파일 관련 syscall의 흐름이 선명해진다.

fdt를 정리한다는 것은 배열 자체를 없앤다는 뜻만이 아니다. fdt에 남아 있는 열린 파일 객체들을 모두 닫아 자원을 반환하는 과정까지 포함한다. 스레드가 사라질 때 fdt 배열 메모리는 같이 사라질 수 있지만, 열린 파일에 대한 `file_close()` 책임은 자동으로 처리되지 않는다.

## 7. 발표용 요약

처음에는 파일 작업을 할 때 파일명을 기준으로 fdt를 찾아 fd를 얻는다고 생각했다.

하지만 Pintos의 파일 syscall 구조에서는 파일명을 사용하는 시점은 `open`이고, `read`와 `write`는 이미 발급된 `fd`를 사용한다. 그래서 `open`에서 `filesys_open()`으로 얻은 `struct file *`를 현재 프로세스의 `fdt`에 저장하고, 이후 syscall들은 fd를 통해 그 파일 객체를 다시 찾는 방식으로 설계를 정리했다.

결론적으로 `fd`는 유저에게 보여주는 정수 핸들이고, `fdt`는 각 프로세스가 가진 커널 내부 자원 테이블이다.

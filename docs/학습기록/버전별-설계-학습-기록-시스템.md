# 버전별 설계 학습 기록 시스템

이 문서는 기능을 구현하면서 생긴 설계 변화, 실수, 대안 선택, 학습 내용을 기록하는 방식이다.

목표는 단순히 "최종 코드가 무엇인가"를 남기는 것이 아니다. 처음에는 어떤 생각으로 접근했고, 어떤 문제가 드러났고, 여러 대안 중 무엇을 왜 선택했는지를 보여주는 것이다. 이 기록은 발표 자료, 회고, 코드 리뷰 준비에 다시 사용할 수 있다.

## 1. 기록의 목적

기능 구현 과정은 보통 한 번에 정답으로 가지 않는다.

처음에는 단순한 코드로 시작하고, 테스트나 코드 읽기를 통해 부족한 점을 발견하고, 그 문제를 해결하기 위해 설계를 바꾼다. 이 과정을 기록하면 다음을 설명할 수 있다.

- 내가 처음에 문제를 어떻게 이해했는가
- 어떤 기준으로 현재 설계가 부족하다고 판단했는가
- 가능한 대안은 무엇이었는가
- 최종적으로 어떤 대안을 선택했고, 왜 선택했는가
- 이 과정에서 새로 배운 개념은 무엇인가

즉 기록의 핵심은 결과가 아니라 판단의 흐름이다.

## 2. 문서 기본 구조

하나의 기능 기록 문서는 다음 구조를 기본으로 한다.

```text
# 기능명 학습과 설계 기록

## 1. 문제 정의
## 2. 구현 전 기초 이론 정리
## 3. 내가 세운 초기 기준
## 4. 버전별 설계 변화
### v1. 최초 접근
### v2. 첫 번째 개선
### v3. 두 번째 개선
## 5. 최종 설계 기준
## 6. 배운 점
## 7. 발표용 요약
```

기능이 작으면 v2까지만 있어도 충분하다. 중요한 것은 버전 수를 늘리는 것이 아니라, 각 버전이 왜 생겼는지 설명하는 것이다.

## 3. 구현 전 기초 이론 정리 방식

완전히 초기 설계와 구현을 시작하기 전에는 먼저 "내가 구현해야 하는 기능"을 추상적으로 적는다. 이 단계에서는 아직 코드 모양을 정하려고 하지 않는다.

예를 들어 다음 정도면 충분하다.

```text
시스템 콜에서 유저가 넘긴 포인터가 안전한지 검사해야 한다.
잘못된 주소가 들어오면 커널이 죽지 않고 프로세스를 종료해야 한다.
```

사용자가 특정 구현 방식이나 제한된 대안을 함께 제시하더라도, 그 프롬프트를 그대로 구현 범위의 한계로 삼지 않는다. 사용자는 현재 알고 있는 개념 안에서 최선을 다해 요청할 수 있으므로, 문서는 먼저 그 요청에 숨어 있는 지식의 한계와 빠진 설계 관점을 점검한다.

이 단계에서는 다음을 확인한다.

- 사용자가 제시한 방식이 기능의 본질을 충분히 설명하는가
- 사용자가 모르는 개념 때문에 더 나은 대안이 프롬프트에서 빠져 있지는 않은가
- A/B 중 하나를 고르는 문제가 아니라, 더 앞단의 설계 기준을 세워야 하는 문제는 아닌가
- Pintos의 기존 구조, 테스트 요구사항, OS 개념을 기준으로 더 적절한 선택지는 없는가
- 구현 전에 학습하면 선택의 질이 높아지는 개념은 무엇인가

목표는 사용자의 요청을 무시하는 것이 아니다. 사용자의 프롬프트를 출발점으로 삼되, 그 안에 갇히지 않고 설계 공간을 넓힌 뒤, 사용자가 더 많은 정보를 바탕으로 구현 방향을 선택할 수 있게 하는 것이다.

그러면 문서의 `2. 구현 전 기초 이론 정리`에는 이 기능을 이해하는 데 필요한 가장 기초적인 이론을 먼저 정리한다.

이론 정리는 다음을 포함하면 좋다.

- 이 기능이 필요한 이유
- 관련된 OS 개념
- Pintos에서 이 기능과 연결되는 구조체, 함수, 파일
- 구현 전에 반드시 조심해야 할 실패 가능성
- 아직 코드로 결정하지 말아야 할 설계 선택지

이 단계의 목표는 정답 코드를 미리 만드는 것이 아니라, 구현을 시작할 때 어떤 개념을 알고 있어야 하는지 바닥을 깔아두는 것이다.

권장 형식은 다음과 같다.

```text
## 2. 구현 전 기초 이론 정리

### 프롬프트의 한계 보정과 설계 확장

### 기능이 필요한 이유

### 관련 개념

### 가능한 설계 대안

### Pintos에서 확인해야 할 코드 위치

### 구현 전 주의할 점

### 아직 열어둘 설계 선택지
```

그 다음 내가 처음 코드로 대충 설계하거나 구현한 내용, 또는 구현 발상을 프롬프트로 넣고 "현재 상태를 문서에 반영해줘"라고 요청하면, 그 내용은 `4. 버전별 설계 변화`의 `v1. 최초 접근`에 기록한다.

반대로 아직 이론을 학습하고 설계 선택지를 검토하는 단계라면 `4. 버전별 설계 변화`에 `v1`, `v2`를 만들지 않는다. 버전은 내가 실제로 작성한 코드나 구체적인 설계 초안을 기준으로 시작한다. 학습만 한 상태에서 나온 대안 비교, 추천 방향, 주의점은 `2. 구현 전 기초 이론 정리`나 `3. 내가 세운 초기 기준`에 남긴다.

## 4. 버전 기록 형식

각 버전은 같은 틀로 작성한다.

```text
### vN. 버전 이름

#### 목표
이 버전에서 해결하려던 문제를 적는다.

#### 코드 또는 구조
해당 시점의 핵심 코드를 짧게 보여준다.

#### 이전 버전에서 개선된 점
이 버전이 이전 버전보다 나아진 점을 적는다.

#### 남은 문제
아직 해결되지 않은 문제, 새로 발견된 위험을 적는다.

#### 가능한 대안
다음 버전으로 넘어가기 전에 고려할 수 있는 선택지를 적는다.

#### 채택한 방향
v2 이후부터는 여러 대안 중 무엇을 선택했는지와 이유를 적는다.
```

최초 버전인 v1에는 "이전 버전에서 개선된 점" 대신 "초기 접근의 장점"을 쓰면 자연스럽다.

버전 번호는 핵심 로직이나 설계 기준이 바뀔 때만 올린다. 예를 들어 검증 단위가 "시작 주소만 검사"에서 "버퍼가 걸치는 모든 페이지 검사"로 바뀌었다면 v1에서 v2로 넘어갈 만하다.

반대로 핵심 로직은 그대로인데 변수명 정리, 중복 제거, 문법 오류 수정, 함수 위치 이동처럼 의미가 크게 바뀌지 않은 수정은 새 버전으로 만들지 않는다. 이런 내용은 해당 버전의 가장 아래에 작은 메모로 남긴다.

권장 이름은 `작은 수정 메모`이다. `오답노트`처럼 실수와 교정을 남기는 용도이지만, 단순 리팩토링이나 문법 수정까지 포함할 수 있게 더 넓은 이름을 쓴다.

```text
#### 작은 수정 메모
- 컴파일 오류 때문에 함수 선언 순서를 조정했다. 설계 자체는 바뀌지 않았다.
- 같은 조건 검사가 반복되어 헬퍼 함수로 분리했다. 포인터 검증 기준은 유지했다.
- 변수명을 `addr`에서 `uaddr`로 바꿔 유저 주소라는 의미를 더 분명히 했다.
```

이 메모는 버전의 핵심 서술보다 작게 다룬다. 목적은 "새 설계가 생겼다"가 아니라 "같은 설계를 다듬는 과정에서 어떤 실수나 정리를 했는지"를 보존하는 것이다.

## 5. 좋은 기록의 기준

좋은 기록은 코드 설명만 하지 않는다. 설계 판단을 같이 남긴다.

예를 들어 "버퍼를 페이지 단위로 검사했다"보다 다음 설명이 더 좋다.

```text
시작 주소만 검사하면 buffer가 페이지 경계를 넘는 순간 다음 페이지가 unmapped일 수 있다.
따라서 buffer부터 buffer + size - 1까지 포함하는 모든 페이지를 검사하도록 바꿨다.
```

이 방식은 내가 어떤 실패 가능성을 발견했고, 그 실패 가능성을 어떤 구조로 제거했는지 보여준다.

## 6. 대안 비교 방식

대안은 최소 두 개 이상 적으면 판단 과정이 선명해진다.

```text
대안 A: 바이트 단위로 모든 주소를 검사한다.
- 장점: 이해하기 쉽고 정확하다.
- 단점: size가 클 때 불필요하게 느리다.

대안 B: 페이지 단위로 검사한다.
- 장점: 페이지 테이블 매핑 단위와 맞고 효율적이다.
- 단점: 시작 주소와 끝 주소 계산을 조심해야 한다.
```

그 다음 채택 이유는 "좋아 보여서"가 아니라 기준에 맞춰 적는다.

```text
Pintos의 주소 매핑은 페이지 단위이고, pml4_get_page도 주소가 속한 페이지의 매핑 여부를 확인한다.
따라서 버퍼 전체를 바이트 단위로 볼 필요 없이, 범위가 걸치는 페이지들을 검사하는 대안 B를 채택했다.
```

## 7. 코드 스니펫 작성 규칙

문서에 코드를 넣을 때는 전체 파일을 붙이지 않는다. 발표나 회고에 필요한 핵심만 남긴다.

권장 형식은 다음과 같다.

```c
static bool
is_valid_user_ptr(const void *uaddr) {
    if (uaddr == NULL)
        return false;
    if (!is_user_vaddr(uaddr))
        return false;
    return pml4_get_page(thread_current()->pml4, uaddr) != NULL;
}
```

코드 아래에는 반드시 그 코드가 보여주는 설계 포인트를 한두 문장으로 설명한다.

## 8. 발표용 요약 작성법

문서 마지막에는 발표에서 바로 사용할 수 있는 짧은 요약을 둔다.

```text
처음에는 포인터 시작 주소만 검사하면 된다고 생각했다.
하지만 버퍼는 여러 페이지에 걸칠 수 있고, pml4_get_page는 유저 주소만 받을 수 있다는 점을 확인했다.
그래서 단일 포인터 검증과 버퍼 범위 검증을 분리하고, 버퍼는 페이지 단위로 순회하는 방식으로 설계를 바꿨다.
```

이 요약은 "무엇을 만들었다"보다 "어떻게 사고가 바뀌었다"를 중심으로 쓴다.

## 9. 체크리스트

새 기능 기록을 만들 때 아래 항목을 확인한다.

- 문제 정의가 있는가
- 구현 전 기초 이론 정리가 있는가
- 최초 접근 코드가 있는가
- 각 버전마다 개선점과 남은 문제가 있는가
- 핵심 로직 변화만 새 버전으로 분리했는가
- 단순 리팩토링, 문법 수정, 작은 실수 교정은 작은 수정 메모로 남겼는가
- 대안을 비교했는가
- 선택한 대안의 이유가 기술적으로 설명되는가
- 마지막에 배운 점과 발표용 요약이 있는가
